Complete code walkthrough

How your autonomous path system actually works

Every file in the path generator, what each line is doing, and — more importantly — why it's built that way. Read it top to bottom once and the whole thing will click; keep it open as a reference after that.

Your autonomous is really two questions bolted together. First: given where the robot is and a list of places it needs to touch, what is the best path that doesn't crash into anything? Second: how do we hand that path to Pedro Pathing and drive it on a real robot with an intake and a shooter?

The whole design is organized around keeping those two questions separate. All the hard thinking — routing, avoiding obstacles, smoothing corners, deciding whether to drive backwards — lives in a set of plain Java classes that know nothing about Pedro, nothing about the FTC SDK, nothing about a real robot. That's the core. On top of it sits a thin bridge that translates the core's answer into Pedro's language, and an OpMode that runs the show.

The one idea to hold onto

The planner is pure: it takes numbers in and gives numbers out, with no robot attached. That single decision is why the desktop visualizer can run the exact same planner code the robot runs — there is no second copy of the logic to keep in sync. When you change how paths are generated, both the robot and the visualizer change together, automatically, on the next build.

00The architecture map

Before any single file, here's how they call each other. Read it as water flowing downhill: the OpMode at the top asks for a path, the request flows down through the bridge into the pure core, the core leans on Field and the obstacle shapes to check for collisions, and a finished path flows back up.

The files fall into seven layers. We'll go bottom-up, because each layer only depends on the ones below it — so by the time you reach the OpMode, every piece it uses will already make sense.

01Coordinates & geometry primer

Two conventions are baked into every file. Get these straight now and nothing later will surprise you.

The field

The field is a 144 × 144 inch square. The origin (0,0) is the bottom-left corner. x grows to the right, y grows up. So the top-right corner is (144,144).

Headings (which way the robot faces)

A heading is an angle in radians, measured the standard math way: 0 points along +x (to the right), and it increases counter-clockwise, so 90° = π/2 points along +y (straight up). Code uses Math.toRadians(90) to write "facing up" without doing the arithmetic by hand.

The robot's "front" leads

Your intake is on the front of the robot. So when the planner drives the robot forward along a path, the front — and therefore the intake — hits each ball first. That's why, all through the core, the default is to point the robot's heading along the direction of travel: "face where you're going" is the same as "lead with the intake." The only time that flips is when driving backwards is faster (more on that later).

02Layer 1 — Obstacles: the shapes to avoid

An obstacle is anything the robot must drive around. There are three concrete kinds — rectangle, triangle, circle — and they all agree to answer the same three questions. That agreement is the Obstacle interface.

Obstacle.java PURE CORE The contract every shape promises to fulfill. PathCore/…/PathGen/core/Obstacle.java 
public interface Obstacle {
    /* Inside the shape? */
    boolean contains(double x, double y);

    /* Inside the shape expanded outward by `margin`? (pass robot radius) */
    boolean contains(double x, double y, double margin);

    /* Route nodes sitting `margin` outside my corners. Each is {x, y}. */
    List<double[]> navPoints(double margin);
}

An interface is a promise, not code. It says "any class that calls itself an Obstacle must have these three methods." Because they all keep that promise, the rest of the program can hold a mixed list of rectangles, triangles and circles and treat them identically — it just calls contains(...) without caring which shape it's talking to. That's what lets you drop a new shape into the field later without touching the planner.

The three questions each shape answers:

  • contains(x, y) — is this point inside me?
  • contains(x, y, margin) — is this point inside me if I grow outward by margin inches? This is the important one: pass the robot's radius as the margin and you're really asking "would the robot's body touch me if its center were here?"
  • navPoints(margin) — give me a handful of points that sit just outside your corners. These become the "stepping stones" the router uses to walk around you.
Why "grow the shape" instead of "shrink the robot"?

The robot isn't a point — it has a body. There are two ways to handle that: check every point of the robot's body against the real obstacle, or treat the robot as a single point and grow every obstacle outward by the robot's size. The second is far simpler and just as safe, so that's what we do everywhere. The margin turns "does the robot fit?" into "is this one point clear?"

RectObstacle.java

RectObstacle.java PURE CORE An axis-aligned box, from lower-left to upper-right corner. PathCore/…/PathGen/core/RectObstacle.java 
public boolean contains(double x, double y, double m) {
    return x >= lcx - m && x <= ucx + m && y >= lcy - m && y <= ucy + m;
}

A rectangle is stored as two corners: (lcx, lcy) lower-left and (ucx, ucy) upper-right. A point is inside when its x is between the left and right edges and its y is between the bottom and top. Growing by m is just subtracting m from the low edges and adding it to the high edges — the box gets m inches bigger in every direction. Simple and exact.

public List<double[]> navPoints(double m) {
    double o = m + 2;   // push corners out past the inflated box
    return Arrays.asList(
        new double[]{ lcx - o, lcy - o },   // the four corners,
        new double[]{ ucx + o, lcy - o },   // each nudged a bit
        new double[]{ ucx + o, ucy + o },   // further out so a
        new double[]{ lcx - o, ucy + o });  // path can hug the corner
}

The nav points are the four corners, each pushed out by the margin plus 2 extra inches. The extra 2 matters: if a stepping-stone sat exactly on the inflated edge, the tiniest rounding error would put it inside the keep-out zone and the router would throw it away. Two inches of breathing room keeps every corner reliably reachable.

TriObstacle.java

TriObstacle.java PURE CORE A triangle from three corners — the building block for odd field shapes. PathCore/…/PathGen/core/TriObstacle.java

Triangles are more flexible than boxes — you build the diamond in the middle of your field out of two of them. A triangle is trickier in two ways: telling whether a point is inside it, and growing it outward.

Growing a triangle: push corners away from the center

A box grows by moving its edges. A triangle grows by moving its corners directly away from the triangle's center point (its "centroid", the average of the three corners). The push helper does exactly that:

private static double[] push(double px, double py, double gx, double gy, double d) {
    double dx = px - gx, dy = py - gy, len = Math.hypot(dx, dy);
    if (len < 1e-9) return new double[]{ px, py };   // corner is the center: nowhere to push
    return new double[]{ px + dx/len * d, py + dy/len * d };
}

It takes the direction from the center (gx,gy) to the corner (px,py), shrinks that direction to length 1 (dividing by len), then steps d inches along it. Result: the corner slides straight outward by exactly d. Math.hypot(dx,dy) is just the distance formula, √(dx²+dy²).

Point-in-triangle: the "same side" test

double d1 = sign(x, y, A, B);   // which side of edge A→B is the point on?
double d2 = sign(x, y, B, C);   // edge B→C
double d3 = sign(x, y, C, A);   // edge C→A
boolean hasNeg = (d1 < 0) || (d2 < 0) || (d3 < 0);
boolean hasPos = (d1 > 0) || (d2 > 0) || (d3 > 0);
return !(hasNeg && hasPos);

Each of the three sign(...) calls answers "is the point to the left or the right of this edge?" (positive = one side, negative = the other — it's a cross-product, the math trick for left/right). Here's the insight: if the point is genuinely inside the triangle, it's on the same side of all three edges — so the three results are all positive or all negative, never mixed. The last line says exactly that: "it's inside unless we saw both a negative and a positive," i.e. unless it fell on different sides of different edges.

CircleObstacle.java

CircleObstacle.java PURE CORE A round keep-out zone — center plus radius. PathCore/…/PathGen/core/CircleObstacle.java 
public boolean contains(double x, double y, double margin) {
    // distance from the CIRCLE'S CENTER (was measuring from origin (0,0) — bug fix)
    return Math.hypot(x - cx, y - cy) <= r + margin;
}

A circle is the easiest shape: a point is inside when its distance from the center is no more than the radius. Growing by margin is literally adding to the radius. Note the comment — this line once measured distance from (0,0) instead of the circle's center, so every circle behaved as if it were at the origin. Small typo, total nonsense results. Worth remembering when something acts bizarre: check that the math is measuring from the thing you think it is.

Why a circle needs 12 nav points, not 4

double rr = r + margin + 3;   // ring just outside the inflated circle
int n = 12;                  // 12, not 8: fewer points and the straight line
for (int i = 0; i < n; i++) {   // between two of them cuts back inside the
    double a = 2*Math.PI*i / n;  // keep-out zone for a big robot → routing fails
    pts.add(new double[]{ cx + rr*Math.cos(a), cy + rr*Math.sin(a) });
}

A box has natural stepping-stones — its corners. A circle has none, so we sprinkle points evenly around a ring just outside it. The router walks between these points in straight lines. Here's the trap: if you only place a few points around the ring, the straight line connecting two neighbors is a chord that dips inward, cutting across the circle. For a big robot with a big keep-out radius, that chord dips right back into the forbidden zone, so the router decides it can't get from one stepping-stone to the next and gives up. Twelve points keep the chords shallow enough to stay clear. This is a real bug that was fixed by bumping 8 → 12.

03Layer 2 — Field: the collision brain

Field.java PURE CORE Holds the obstacles and answers every "can the robot be / go here?" question. PathCore/…/PathGen/core/Field.java

Field is the one place that knows everything about what's solid. The planner never talks to obstacles directly — it asks the Field. That keeps all the collision logic in a single file.

The robot's size becomes a single number: its radius

public Field(double robotWidth, double robotLength) {
    // half the diagonal = worst-case radius no matter which way the robot faces
    this.robotRadius = 0.5 * Math.hypot(robotWidth, robotLength);
    this.robotWidth  = robotWidth;
    this.robotLength = robotLength;
}

This is the single most important idea in the whole collision system. The robot is a rectangle, and as it turns, the rectangle sweeps out different shapes. Rather than track that, we wrap the robot in the smallest circle that always contains it — and the radius of that circle is half the diagonal of the rectangle. A 15.5 × 17.5 robot gives a radius of about 11.7 inches.

Why the bounding circle is worth its slight waste

A circle looks the same from every angle. So if we keep the robot's center at least radius inches from everything solid, the robot is guaranteed to fit no matter which way it's facing. That means the planner never has to think about heading when checking collisions — a huge simplification. The cost is that the corners of the circle stick out past the real robot, so it's slightly more cautious than strictly necessary. For a competition robot that trade is almost always worth it.

Two kinds of "blocked" — and why there are two

public boolean blocked(double x, double y) {
    // walls: the robot center can't get within its radius of an edge
    if (size > 0 && robotRadius > 0 &&
            (x < robotRadius || x > size-robotRadius ||
             y < robotRadius || y > size-robotRadius)) return true;
    return blockedByObstacle(x, y);
}

public boolean blockedByObstacle(double x, double y) {
    double m = clearance();                       // robotRadius + minClearance
    for (Obstacle o : obstacles) if (o.contains(x, y, m)) return true;
    return false;
}

There are two questions, and the difference between them is the key to how wall-ball intaking works:

  • blocked = "the robot center physically cannot be here." This includes the obstacles and the strip around the field edge that the center can't reach because the robot's body would be stuck in the wall. This is the strict, everyday check used for normal driving.
  • blockedByObstacle = "there's a real obstacle here" — but it ignores the walls.
Why ignore the walls sometimes?

Because a ball can sit right up against a wall — in the strip the robot's center can't reach. To grab it, the robot deliberately noses its front into that strip. During that one deliberate move, we don't want the wall counting as an obstacle (of course the front is near the wall — that's the point). So the intake move uses blockedByObstacle (ignore walls, still respect real obstacles), while everything else uses blocked (respect walls too). Same field, two lenses.

inWallStrip — is a ball in the hard-to-reach edge?

public boolean inWallStrip(double x, double y) {
    if (size <= 0 || robotRadius <= 0) return false;
    boolean onField  = x >= 0 && x <= size && y >= 0 && y <= size;
    boolean nearWall = x < robotRadius || x > size-robotRadius
                    || y < robotRadius || y > size-robotRadius;
    return onField && nearWall && !blockedByObstacle(x, y);
}

This returns true for a point that is on the field, close enough to a wall that the center can't reach it, but not sitting inside a real obstacle. In other words: "a ball here needs the special wall-intake approach." The planner calls this to decide whether an ordinary drive-through will work or whether it has to set up a nose-in maneuver.

Checking a whole line, not just a point

public boolean segmentClear(double x1,double y1,double x2,double y2, boolean wallAware){
    double dist = Math.hypot(x2-x1, y2-y1);
    int samples = Math.max(2, (int) dist);          // ~1 check per inch
    for (int i = 0; i <= samples; i++) {
        double t = i / (double) samples;
        double px = x1 + (x2-x1)*t, py = y1 + (y2-y1)*t;
        if (wallAware ? blocked(px,py) : blockedByObstacle(px,py)) return false;
    }
    return true;
}

"Can the robot drive straight from A to B?" We can't check infinitely many points, so we sample: walk from A to B in roughly one-inch steps and check each spot. t slides from 0 to 1, and A + (B−A)·t is the point that fraction of the way along — that's linear interpolation, a pattern you'll see again in the smoothing and the visualizer. The wallAware flag picks which of the two "blocked" lenses to use, so the same routine serves both normal driving and the deliberate intake dip.

The one risk of sampling

Sampling every inch could, in theory, "step over" an obstacle thinner than an inch. None of your field obstacles are that thin, so it's safe here — but it's the reason the check is fast. It's a deliberate trade of perfect precision for speed, which matters when the planner runs this thousands of times per path.

04Layer 3 — Seg & GeoResult: the plain-data answer

These two classes hold no logic at all. They're just containers — the shape of the planner's answer. Keeping the answer as plain numbers (no Pedro types) is what lets the visualizer and the robot share it.

Seg.java PURE CORE One drivable piece of a path: a curve or a straight line, with a heading at each end. PathCore/…/PathGen/core/Seg.java 
public final double x1, y1, h1;          // start point + heading (radians)
public final double x2, y2, h2;          // end point + heading
public final boolean curve;              // true = Bezier curve, false = straight
public final double c1x, c1y, c2x, c2y;  // curve control points (only if curve)

A full path is a list of Segs laid end to end. Each one is either a straight line (start point, end point) or a cubic Bézier curve. A Bézier is a smooth curve defined by four points: the two endpoints plus two "control points" that pull the curve toward them like magnets without the curve ever actually touching them. That's how the planner rounds off sharp corners. Each segment also carries the heading the robot should hold at its start and end.

Notice final on every field: once a Seg is created it can never change. That's on purpose — an answer that can't be accidentally modified after the fact is one less source of bugs. The two factory methods Seg.straight(...) and Seg.curved(...) just make it obvious which kind you're creating.

GeoResult.java PURE CORE The whole answer: the segments, the raw route, notes — and whether it succeeded. PathCore/…/PathGen/core/GeoResult.java 
public enum Status { OK, ADJUSTED, FAILED }

public final Status status;
public final List<Seg> segs;         // the drivable pieces, in order
public final List<double[]> route;   // the raw corner points (for drawing)
public final List<String> notes;     // what got adjusted, or why it failed
The rule that keeps auto from ever crashing

Look at the three statuses. The planner never throws an error — it always returns one of these. OK means "planned exactly what you asked." ADJUSTED means "I had to nudge something, but here's a usable path — read notes to see what I changed." FAILED means "I couldn't do it; segs is empty, use a fallback." Because a bad plan comes back as a value instead of a crash, your OpMode can look at it, shrug, and try again next loop instead of the whole autonomous dying. In a 30-second match, "try again" beats "crash" every time.

GeoResult is the pure-core answer. Its twin, PathResult (Layer 5), is the same idea but holding a real Pedro path instead of raw segments — the bridge converts one into the other.

05Layer 4 — PlanEngine: the brain

PlanEngine.java PURE CORE Turns a list of points into a smooth, collision-free, drivable path. The heart of everything. PathCore/…/PathGen/core/PlanEngine.java

This is the big one — about 430 lines. But it's built from small, understandable pieces, and it has exactly three public "front doors":

  • plan(waypoints) — drive forward through every point, front leading. The simplest mode.
  • planReturn(from, to, heading) — a single leg that automatically decides whether to drive forward or reverse, whichever is faster.
  • planWithReturn(waypoints) — the one your auto uses: one continuous path through all the balls to the goal, handling wall-balls and auto-reversing the last leg. Built out of the other two ideas.

A few tunable knobs sit at the top:

public double Vx = 76;         // forward/back speed, in/s (the fast axis)
public double Vy = 52;         // strafe speed, in/s (the slow axis)
public double catmullTension = 6.0;   // how gentle the curve smoothing is
public double turnRate = 4.0;        // rough turn speed, rad/s, for cost estimates

These describe how your robot actually moves. A mecanum/omni robot drives forward faster than it strafes sideways, so Vx > Vy. The planner uses these to estimate travel time when it decides between two options — they don't need to be perfect, just roughly right relative to each other.

The simple mode: plan(waypoints)

Everything else is a variation on this, so understand it first. It does four things in order:

1. Un-stick every waypoint. If a requested point sits inside an obstacle (or an unreachable spot), slide it out to the nearest clear spot:

if (field.blocked(w[0], w[1])) {
    double[] freed = nudgeOut(w[0], w[1]);
    if (freed == null)
        return GeoResult.failed("waypoint " + i + " is stuck inside an obstacle");
    notes.add("waypoint " + i + " moved ...");   // tells you it adjusted
    pts.add(freed);
}

2. Connect consecutive points. For each pair, if a straight line between them is clear, use it. If not, call routeAround to find a way around the obstacle:

if (field.isSegmentClear(a, b)) {
    leg = [a, b];                        // straight shot works
} else {
    leg = routeAround(a, b);             // go around
    if (leg == null) return GeoResult.failed(...);
}

3. Assign headings. tangentHeadings makes each point face the next one (front leads = forward driving).

4. Smooth it. buildSegs rounds the sharp corners into curves. Then it returns OK (nothing adjusted) or ADJUSTED (with notes).

The whole method is wrapped in a try/catch that turns any unexpected error into a FAILED result — the "never crash" promise, enforced.

Going around things: visibility graph + Dijkstra

When a straight line is blocked, routeAround finds the shortest way around. This is the single cleverest piece of the planner, and it's a classic two-step algorithm.

Step 1 — build a "visibility graph." Collect a set of nodes: the start, the goal, and every obstacle's nav points (those stepping-stones from Layer 1). Two nodes are "connected" if the robot can drive a clear straight line between them. Picture a web of legal straight-line hops between corners.

Step 2 — Dijkstra's algorithm finds the shortest chain of hops from start to goal:

for (int it = 0; it < n; it++) {
    // pick the un-visited node we can currently reach most cheaply
    int u = /* node with smallest dist[] */;
    done[u] = true;
    if (u == 1) break;                 // reached the goal (node 1) — stop
    for (int v = 0; v < n; v++) {       // try improving every neighbor
        if (!field.isSegmentClear(a, b)) continue;   // only real, clear hops
        double d = dist[u] + Math.hypot(...) / Vx;   // cost = time to get there
        if (d < dist[v]) { dist[v] = d; prev[v] = u; }   // found a better way in
    }
}

Dijkstra keeps, for every node, the cheapest known cost to reach it (dist) and which node you came from (prev). It repeatedly locks in the cheapest un-finished node and uses it to improve its neighbors. When the goal is locked in, walking prev backwards from the goal spells out the shortest route. Cost is measured as time (distance / Vx), not raw distance — a small detail that keeps it consistent with the speed-aware decisions elsewhere.

Why nav points that sit "just outside plus 2 or 3"?

This ties back to Layer 1. If a stepping-stone were exactly on the inflated edge, the clear-line check between it and its neighbor might fail on rounding. The extra couple inches guarantee the corners of the web actually connect, so Dijkstra can find a route instead of reporting "no way through."

nudgeOut — freeing a stuck point

for (double rad = 2; rad <= 48; rad += 2)        // spiral outward…
    for (int a = 0; a < 16; a++) {                 // …in 16 directions
        double ang = 2*Math.PI*a/16;
        double nx = x + rad*Math.cos(ang), ny = y + rad*Math.sin(ang);
        if (!field.blocked(nx, ny)) return new double[]{ nx, ny };
    }
return null;   // truly boxed in (48 inches of solid all around) — give up

If a point is stuck inside an obstacle, this searches outward in growing rings (2, 4, 6… inches) checking 16 directions at each radius, and returns the first clear spot it finds — which is the nearest clear spot, because it grows the radius slowly. If it gets 48 inches out and still finds nothing, it returns null and the caller reports FAILED. Because "clear" uses the bounding circle, the freed spot is valid at any heading.

Smoothing corners into curves

After routing, the path is a polyline — straight segments with sharp corners. A robot can't drive a sharp corner smoothly, so buildSegs replaces each corner with a gentle curve, but only if that curve stays clear of obstacles.

double[] cp = clearControlPoints(p0, p1, p2, p3);
if (cp != null)  segs.add(Seg.curved(...));    // smooth curve fits
else            segs.add(Seg.straight(...));  // no room — stay straight

The curve is a Catmull-Rom style spline: each corner's control points are computed from its neighbors (p0 and p3), so the curve naturally flows in the direction the path is already going. The catmullTension knob controls how far the control points reach — smaller means a rounder, more relaxed curve.

double[] tensions = { catmullTension, 10, 18, 30, 60 };
for (double k : tensions) {
    // build control points at this tension…
    if (curveIsClear(...)) return controlPoints;   // first clear one wins
}
return null;   // even the tightest curve clips something → caller uses a straight line
The clever fallback ladder

It tries the roundest curve first. If that curve would clip an obstacle, it tries progressively tighter curves (tension 10, 18, 30, 60) that hug the corner more closely. The first one that's clear wins. If even the tightest is blocked, it gives up on curving and uses a plain straight line. So you get the smoothest ride the obstacles allow, and never a curve that cuts a corner into a wall. curveIsClear checks by sampling 20 points along the Bézier — the same "sample and check" idea as segmentClear.

The speed model: why reverse can be faster

To decide between forward and reverse, the planner needs to estimate how long each would take. That's what the speed model is for.

private double effSpeed(double theta) {           // theta = angle between travel & the robot's axis
    double c = Math.cos(theta)/Vx, s = Math.sin(theta)/Vy;
    return 1.0 / Math.sqrt(c*c + s*s);           // full Vx along axis, down to Vy sideways
}

Your robot moves fastest straight forward/back (Vx) and slowest sideways (Vy). For any in-between direction, the true speed is somewhere between — and this formula (the equation of an ellipse) gives it. When travel lines up with the robot's facing, theta = 0 and you get full Vx; when travel is sideways, theta = 90° and you get Vy.

private static double axisAngle(double a) {
    double t = Math.abs(wrap(a));
    if (t > Math.PI/2) t = Math.PI - t;   // 0..90°: forward and reverse are equally fast
    return t;
}

This folds any angle into the 0–90° range, which encodes a physical truth: driving forward along an axis and driving backward along it are equally fast. That's the mathematical reason the robot is allowed to consider reversing at all. (wrap just keeps angles in the −180°…180° range so the arithmetic behaves.)

Forward vs. reverse: planReturn

Imagine the robot drives up to a ball facing north, grabs it, and now has to go back to a goal that's south. It could spin 180° and drive forward — or just drive backward without turning at all. Often the second is much faster. planReturn computes both costs and picks the winner.

// FORWARD: turn to face the path, then drive the fast axis the whole way
double turn = Math.abs(wrap(firstTangent - incomingHeading));
double fwdCost = turn/turnRate + len/Vx;

// REVERSE: keep the current heading; speed drops where travel isn't along it
double revCost = 0;
for (each piece of the route)
    revCost += segLength / effSpeed(axisAngle(travelDir - incomingHeading));

boolean reverse = revCost < fwdCost;   // cheaper wins

Forward's cost is "time to spin to face the path" plus "time to drive it at full speed." Reverse's cost skips the spin entirely (it holds the heading the robot already has) but may travel partly sideways, so it uses effSpeed to account for the slowdown. Whichever total time is smaller wins, and lastReturnReversed records the choice so your telemetry can show it. Either way it writes a note explaining the decision and the two estimates — so when you read the driver station you can see why it chose what it did.

The main event: planWithReturn

This is what your auto actually calls. It produces one continuous path: start → ball 1 → ball 2 → ball 3 → goal, flowing through the balls without stopping, and auto-reversing the final leg into the goal if that's faster. It does its job in four phases.

Phase 1 — turn waypoints into "stops." A normal ball is one stop. But a ball in the wall strip can't be driven straight through — so it's expanded into three stops: a staging point outside the strip, the intake center (nose on the ball, at a forced heading), then back out to staging.

if (i > 0 && i < last && field.inWallStrip(w[0], w[1])) {
    double[] ia = chooseIntake(w, prev);          // {stageX,stageY, centerX,centerY, heading, strat}
    if (ia != null) {
        sp.add(staging);   sh.add(NaN);   sd.add(false);   // drive to staging (normal)
        sp.add(center);    sh.add(heading);sd.add(true);    // dip in — straight, ignore wall
        sp.add(staging);   sh.add(NaN);   sd.add(true);    // dip back out
        continue;
    }
}

The three parallel lists carry, for each stop: its position (sp), a forced heading or NaN meaning "just face where you're going" (sh), and whether this is a "dip" leg (sd) that should ignore walls and go straight in. NaN — "not a number" — is used here as a clean flag for "no forced heading."

Phase 2 — route between the stops into one flat list of points, remembering where the final leg to the goal begins. Dip legs go straight (ignoring walls); everything else uses the normal straight-or-routeAround logic.

Phase 3 — assign headings. Start with tangents (face the next point), then override any stop that demanded a forced heading (the intake dips).

Phase 4 — decide the final leg's direction:

boolean directReturn = (n-1 - finalLegStart) == 1;   // last leg is a single straight shot?
boolean reverse = directReturn && revCost < fwdCost;
if (reverse) /* hold the heading instead of spinning */;
Why only reverse a "direct" final leg

Reversing only makes sense when the last leg is a clean straight shot home — a there-and-back where spinning would be wasted motion. If the path to the goal had to curve around an obstacle (multiple points), reversing the whole arc gets confusing and rarely helps, so the code requires directReturn before it'll even consider it. It's the same forward-vs-reverse cost comparison as planReturn, just applied to the tail of one big path.

Wall-ball intaking: chooseIntake

When a ball sits against a wall, chooseIntake figures out how to grab it. It considers two strategies and picks the cheaper one.

  • Head-on: point the front straight at the wall and drive in until the front touches the ball. The center stops half the robot's length short of the ball.
  • Wall-ride: put a side against the wall and drive along the wall, so the front sweeps into the ball from the side.

First it works out which wall the ball is nearest and builds two directions: n, the inward normal (pointing away from the wall, into the field), and ax, the along-wall axis. Then it places the intake geometry off those two directions:

// head-on: face the wall, front on the ball, center L/2 back from it
double hoCx = bx + nx*(L/2),  hoCy = by + ny*(L/2);
double hoHd = Math.atan2(-ny, -nx);                 // heading points AT the wall
double hoSx = bx + nx*stageOff, hoSy = by + ny*stageOff;   // staging, safely out

Math.atan2(y, x) turns a direction into a heading angle — it's the reverse of "cos/sin turn an angle into a direction." Here atan2(-ny, -nx) gives the heading that points at the wall (opposite the inward normal), so the front leads into the ball.

Then it costs both strategies and validates them:

double hoCost = dist(from → staging) + 2*dist(staging → center);   // in and back out
boolean useHo = (both valid) ? hoCost <= wrCost : (whichever is valid);

The cost is the drive to staging plus the in-and-out dip (hence the ×2). intakeValid makes sure the staging point is reachable, the dip line is clear of real obstacles, and the center is actually on the field. If neither strategy is valid, it returns null and the caller falls back to nudging the ball inward instead. Whichever is cheaper and legal wins.

Honest status

Head-on is fully verified: a ball at the bottom wall produces a center exactly half a robot-length above it, front pointed down — correct. Wall-ride is an approximate first version and rarely wins the cost comparison as written, so in practice you'll almost always see head-on. If real matches show certain balls need the side-approach, that's the piece to refine.

06Layer 5 — The Pedro bridge

The core speaks in plain Segs. The robot speaks Pedro Pathing. These files are the translator — and this is the boundary between "pure logic" and "real robot."

PathResult.java PEDRO BRIDGE Same idea as GeoResult, but holding a real Pedro PathChain. TeamCode/…/PathGen/Utilities/PathResult.java

Identical shape to GeoResult — OK / ADJUSTED / FAILED, never thrown — except path is a Pedro PathChain instead of raw segments. usable() returns true when the path isn't null. This is the object your OpMode inspects before driving.

PathPlanner.java PEDRO BRIDGE Runs the pure engine, then converts its segments into a Pedro PathChain. TeamCode/…/PathGen/Utilities/PathPlanner.java

This is a thin wrapper. It exposes the same three front doors as PlanEngine (plan, planReturn, planWithReturn), and each does the same two steps: run the pure engine, then hand the result to toResult to translate. The translation is the only Pedro-specific code in the whole path system:

for (Seg s : g.segs) {
    if (s.curve)
        builder.addPath(new BezierCurve(p1, ctrl1, ctrl2, p2));   // our curve → Pedro curve
    else
        builder.addPath(new BezierLine(p1, p2));                  // our line  → Pedro line
    builder.setLinearHeadingInterpolation(s.h1, s.h2);            // turn smoothly across the seg
    builder.setTValueConstraint(endTValue);                       // how close counts as "done"
}

Each of our Segs becomes one Pedro path piece; a curve maps to a BezierCurve, a line to a BezierLine. setLinearHeadingInterpolation tells Pedro to rotate evenly from the start heading to the end heading across that piece.

The endTValue knob — your fix for "stuck at the end"

setTValueConstraint(0.94) is the antidote to the robot freezing just short of the goal and never firing. Pedro measures progress along a path from 0 (start) to 1 (end). Its default requires ~0.99 — so tight the robot often settles at 0.98 and Pedro never says "done," so the next command (firing) never runs. Lowering it to 0.94 means "94% of the way there counts as arrived." Because the turret aims for you, being a couple inches short doesn't hurt scoring — but it does let the sequence advance. Raise it toward 0.99 for tighter stops, lower for snappier ones.

The deeper fix that lives in Constants.java

There's a second half to this. Pedro also has a "stuck escape" that force-completes a path when the robot stops moving — but it's capped so it only triggers between 10% and 80% of the path. A robot stalled at 96% is past the cap, so the escape never fires. The real cure is raising stuckTValueHigh to 0.99 in your FollowerConstants (in Constants.java). That file is too deeply nested for me to edit from here — it's the one change still on your plate.

SafeDrive.java PEDRO BRIDGE · UNUSED An older "complete on arrival" follower — kept in the tree but not called. TeamCode/…/PathGen/Utilities/SafeDrive.java

This was an earlier attempt at the stuck-at-the-end problem: a follow command that finishes when the robot gets near the target (or stalls), instead of trusting Pedro's tolerance. It works, but you preferred fixing Pedro's own tValue setting instead — cleaner, since it uses the built-in mechanism rather than second-guessing it. The file's still there in case you ever want the arrival-based backstop, but the auto doesn't use it. Nothing wrong with leaving a working spare in the drawer; just know it's not in the live path.

07Layer 6 — RandomPointAuto: the OpMode

RandomPointAuto.java OPMODE The actual autonomous. Wires up hardware, builds the field, loops forever making and driving paths. TeamCode/…/PedroAuto/RandomPointAuto.java

This is a test harness: it drives to random points forever so you can watch the planner behave on a real robot. It's where all the layers below finally get used.

The start pose, computed from the robot's size

private final Pose startPose =
        new Pose(144 - ROBOT_WIDTH/2, ROBOT_LENGTH/2, Math.toRadians(90));
Why the start pose is calculated, not typed in

The robot starts jammed in the bottom-right corner, facing up. Facing up, its width runs along x (against the right wall at x=144) and its length runs along y (against the bottom wall at y=0). So the robot's center sits half a width in from the right and half a length up from the bottom: (144 − W/2, L/2) = about (136.25, 8.75). Typing a guessed number here was the original cause of the robot slamming into walls — the code thought it started somewhere it didn't, so every path was offset. Deriving it from the dimensions means it stays correct even if you change the robot size. Whatever you type here must match where you physically place the robot, or the whole run is shifted by the difference.

Setup, once, before the match

Scheduler.reset();
follower = Constants.createFollower(hardwareMap);
follower.setStartingPose(startPose);
pinpoint.recalibrateIMU(); sleep(1000);        // let the gyro settle

field = new Field(ROBOT_WIDTH, ROBOT_LENGTH)
        .add(new RectObstacle(...))
        .add(new TriObstacle(...))            // the field's shapes, in inches
        ...;
field.minClearance(3);                        // 3 inches of breathing room on top of the body
planner = new PathPlanner(field);

The obstacles you add here are the whole "map" the planner sees. Note the chained .add(...) calls — that works because each returns the field itself (look back at Field.add). minClearance(3) adds 3 inches to the bounding-circle radius, so the planned path keeps a comfortable margin, not a paint-scraping one.

The main loop

while (opModeIsActive()) {
    follower.update();              // Pedro drives the current path one step
    Scheduler.execute();           // run any scheduled commands (fire, intake, …)
    if (!busy && scheduleNewPath()) busy = true;   // idle? make a new path
    // … telemetry …
}

This is the heartbeat. Every cycle it nudges Pedro forward, runs the command scheduler, and — only when it's not already driving (!busy) — asks for a fresh path. The busy flag is what stops it from piling ten paths on top of each other; it flips back to false at the very end of each path's command sequence.

Building and scheduling one path

b1 = randomValidPoint(cur, BALL_SPACING);   // three random "balls"
b2 = randomValidPoint(b1,  BALL_SPACING);
b3 = randomValidPoint(b2,  BALL_SPACING);
waypoints = [cur, b1, b2, b3, END];

PathResult path = planner.planWithReturn(follower, waypoints);
if (!path.usable()) return false;         // couldn't plan → try again next loop

steps = sequential(
    follow(follower, path.path, true),   // drive the whole path
    intake.transferOn(),                // at the goal: fire
    waitMs(FIRE_MS),                    // hold 1 second
    intake.transferOff(),               // stop firing
    intake.intakeOn(),                  // resume intaking for the next run
    () -> busy = false                   // allow a new path to be made
);
schedule(steps);

This reads like a to-do list because that's exactly what Ivy's sequential makes: run the follow, then fire, then wait a second, then reset for the next lap. The final step flips busy back to false, which is the loop's cue to plan again. If planning failed, it returns without setting busy, so the loop simply retries next cycle with fresh points — the "never crash, just retry" philosophy in action.

Generating a valid random point

for (int i = 0; i < 300; i++) {
    double x = lo + rng.nextDouble()*(hi-lo);
    double y = lo + rng.nextDouble()*(hi-lo);
    if (field.blockedByObstacle(x, y)) continue;   // reject only real obstacles — walls are OK!
    best = {x, y};
    if (dist(best, from) >= minAway) return best;   // far enough from the last one
}
Why it checks blockedByObstacle, not blocked

This is the change you specifically asked for. It rejects points inside real obstacles, but allows points in the wall strip — because a ball can legitimately be against a wall, and the planner now knows how to grab those with the head-on/wall-ride intake. If it used blocked instead, it would refuse to ever place a ball near a wall, which isn't how the real field works. It tries up to 300 times to find a point that's also at least minAway from the previous one (so the three balls spread out); if it can't, it returns the last clear point it found rather than looping forever.

08Layer 7 — PathVizApp: the desktop visualizer

PathVizApp.java DESKTOP TOOL A laptop app that runs the real planner so you can see paths without a robot. PathViz/…/pathviz/PathVizApp.java

This is the payoff for keeping the core pure. It's a Java Swing window (Swing is Java's built-in desktop UI toolkit — no install needed). You drop obstacles and waypoints with the mouse, and it draws the planned path live. Crucially, it builds a real Field, adds real obstacles, and calls the real PlanEngine — the same classes the robot compiles:

void recompute() {
    Field f = new Field(robotW, robotL).minClearance(minClear);
    for (Shape s : shapes) f.add(s.toObstacle());   // UI shapes → real Obstacles
    PlanEngine eng = new PlanEngine(f);
    lastResult = eng.plan(wp);                     // the SAME engine the robot runs
    buildTrace(); repaint();
}
There is no second copy of the logic

This is the whole reason the architecture is shaped the way it is. The visualizer can't drift out of sync with the robot, because it isn't a reimplementation — it literally imports and runs org…PathGen.core.PlanEngine. Change the planner, rebuild, and the visualizer shows the new behavior. If it looks right on your laptop, it'll drive that way on the robot (physics aside).

The rest of the file is drawing and interaction, and it splits into a few clear jobs:

  • The coordinate transform (px, py, ix, iy): converts inches ↔ screen pixels. Note py flips y (side − y·scale) because screens count y downward while the field counts it upward. That one flip is what makes "up" on the field look like "up" on screen.
  • The UI Shape classes (CircleShape, RectShape, TriShape): the draggable editor versions of your obstacles. Each has a toObstacle() that produces the real core obstacle. They're separate from the core shapes because they carry editor-only stuff like drag handles.
  • Playback (buildTrace, poseAt, tick): samples the path into points and animates a robot rectangle gliding along it at Vx, so you can watch the motion, not just the line.
  • The sidebar: sliders and checkboxes for robot size, clearance, and overlays (the inflated keep-out zones, nav points, the visibility graph). Turning on "visibility graph" literally draws the web of clear straight-line hops that Dijkstra searches — a great way to see the routing think.

You run it with ./gradlew :PathViz:run or the green Run arrow on the file in Android Studio. It's the fastest way to sanity-check a planner change before ever touching the robot.

09The pieces it plugs into (not ours)

A few names in the OpMode belong to code you already had. The path system just calls them:

  • Intake — intakeOn(), transferOn(), transferOff(). The front collector and the kicker that feeds the shooter.
  • Shooter — startVelPID(...) holds the flywheel at a target speed; startTurretTracking(follower) keeps the turret aimed at the goal as the robot moves.
  • Constants — Pedro's tuning (including createFollower and the FollowerConstants where stuckTValueHigh lives).
  • GoBildaPinpointDriver — the odometry pod computer that tells Pedro where the robot is.

These aren't part of the path generator and the walkthrough leaves their internals alone — but knowing which calls are "yours already" versus "the planner" helps when you read the OpMode.

10One path, from click to wheels

Here's the whole system in a single trip, tying every layer together:

  1. The loop sees busy == false and calls scheduleNewPath().
  2. randomValidPoint asks Field.blockedByObstacle three times to pick three balls that aren't inside real obstacles (walls allowed).
  3. The OpMode calls planner.planWithReturn(follower, [start, b1, b2, b3, goal]).
  4. The bridge runs the pure PlanEngine.planWithReturn. For any wall-ball, chooseIntake builds a staging→center→staging dip. Between stops, routeAround runs Dijkstra over the visibility graph (built from Field's obstacle nav points) when a straight line is blocked.
  5. tangentHeadings points each stop at the next; forced intake headings override where needed; the final leg's forward-vs-reverse is decided by the effSpeed cost model.
  6. buildSegs rounds the corners into Béziers that curveIsClear confirms are safe, and returns a GeoResult full of Segs.
  7. The bridge's toResult converts each Seg into a Pedro BezierCurve/BezierLine, stamps setTValueConstraint(0.94) on each, and wraps it in a PathResult.
  8. The OpMode schedules: follow the path → fire → wait → resume intake → clear busy.
  9. follower.update() drives it out on the wheels; when it reaches ~94% of the end, the follow completes, the shooter fires, and the loop plans the next one.

Every layer did one job and handed a clean result to the next. That's the design working as intended.

The mental model to keep

If you remember one thing: logic lives in the pure core, robot-specific translation lives in the bridge, and the OpMode just wires it together. When something's wrong, that tells you where to look.
